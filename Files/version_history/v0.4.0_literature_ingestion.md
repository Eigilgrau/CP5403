## Code Flow and Decisions

### 1. Inventory and Source Identity

Each PDF receives a SHA-256 fingerprint and a document ID derived from it. Metadata includes the original filename, page count, available PDF properties and source-policy metadata. A changed PDF creates a different identity. Reviewed policies match the full fingerprint, preventing an unrelated file with the same name from silently inheriting a layout or approval decision.

The source policy supplies bibliographic details verified from the available paper. Unrecognised papers default to an unreviewed layout and remain unapproved for diagnostic use. Their extraction must be inspected before corpus inclusion.

### 2. Extract Blocks and Restore Reading Order

PyMuPDF extracts original text blocks and coordinates. The Charan paper's PDF object order placed right-column text before the abstract and other left-column content. The reviewed policy sorts left then right within bands separated by full-width text blocks. A rendered page sample and ordered paragraph previews in the notebook allow this choice to be checked visually.

Headers, footers, figures, captions, affiliations, manually identified tables on PDF pages 9 and 10, and declarations/references on pages 14 and 15 are excluded from accepted prose. Their text remains in `block_audit.jsonl`, with raw text, coordinates and reasons. Image and detected-table regions are recorded separately. Tables in this PDF are not reliably captured by automatic table detection, which is why the source-specific rectangles are explicit.

No OCR or table interpretation is performed. Complete coverage refers to the accepted prose, not every visual object in the PDF. Source fidelity is checked against canonical extracted text. It is not a guarantee that automated extraction reproduces every visual reading correctly.

Canonicalisation collapses whitespace and removes discretionary soft hyphens. Visible line-end hyphens are preserved and flagged rather than guessed away. Original block text is retained so this transformation can be audited. Section metadata is inferred conservatively from numbered headings and may be incomplete at page or paragraph boundaries.

### 3. Assign Sentence Units and Enforce Encoder Limits

Sentence segmentation uses conservative punctuation boundaries with common abbreviation exceptions. Each unit stores its document, paragraph, sentence and unit IDs; page; section; bounding box; and exact start/end character offsets into its canonical paragraph. Oversized sentences become consecutively identified fragments. Fragment status is explicit, and reconstruction checks ensure no text is lost.

The embedding choice is `sentence-transformers/all-MiniLM-L6-v2`, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`. Only its tokenizer and configuration are needed at this stage; embedding weights and retrieval vectors are not loaded or created. Model assets have expected SHA-256 hashes.

The sentence-transformer configuration specifies **256 tokens**, while the underlying tokenizer advertises 512. The smaller encoder limit governs construction. Token counts include special tokens and disable truncation. Chunks target 220 tokens and must never exceed 256. Future embeddings must encode the chunk's `text` field under this contract; prepending titles or metadata requires a fresh budget check.

The baseline retains paragraph boundaries and splits long paragraphs at sentence or fragment boundaries. It has no overlapping units. This makes coverage checks explicit, although short headings and paragraph continuations can create weak standalone chunks. Their semantic adequacy remains part of inspection rather than being assumed from structural validity.

### 4. Prepare Qwen Boundary Requests

The selected generator is `Qwen/Qwen3-4B-Instruct-2507`, revision `cdbee75f17c01a7cc42f958dc650907174af0554`. The same checkpoint is intended for later diagnosis; this stage only prepares and optionally runs chunking prompts with fixed weights. Neither fine-tuning nor RAG is used for boundary selection.

Requests are grouped by available section metadata and limited to 32 units or approximately 1,600 summed embedding-token counts. The prompt asks for a JSON object containing only `chunk_end_ids`. Each ID closes a consecutive chunk, starting from the first unit and ending at the last. Python reconstructs the source text; Qwen does not write, paraphrase or summarise it. No generated labels or summaries are stored as source evidence.

The validator rejects invalid JSON, extra keys, empty lists, non-string IDs, unknown IDs, duplicated or unordered boundaries, omitted trailing text and chunks over the actual embedding limit. The request ID fingerprints the full prompt, settings, model revision and embedding revision. Prompt or setting changes therefore produce new cache keys.

### 5. Cache and Resume

Extraction cache keys include the PDF hash, source policy, extraction version, PyMuPDF version and module fingerprint. Cached payloads carry their own integrity digest. Qwen responses are saved atomically after each batch and include their actual origin, raw response, revision, runtime, token counts and duration. These files belong on Drive for Colab use.

Missing inference becomes `qwen_not_run`. Invalid boundaries or runtime errors become paragraph fallback with a recorded reason. `chunks_qwen_candidate.jsonl` can therefore contain a mixture of actual Qwen-selected boundaries and explicit fallbacks. It must never be reported wholesale as successful Qwen output. Synthetic fixtures are rejected as actual model-inference provenance.

### 6. Colab Execution and Pending Checks

Upload the notebook, both modules, source policy, requirements files, test module and paper into the documented Drive structure. Preserve `Datasets/PHM15-literature` to resume caches. In the notebook, set `RUN_QWEN = True` and initially leave `MAX_REQUESTS = 3`. After checking the pilot, set `MAX_REQUESTS = None` to process remaining uncached requests. Rerun `run_stage()` to validate cached outputs and reconstruct candidate chunks.

The runner uses NF4 4-bit loading, double quantisation, float16 compute and greedy generation. Input is capped at 6,000 Qwen tokens without truncation; output is capped at 1,200 tokens. Exact GPU, packages, model loading cost and per-request timings are recorded. Out-of-memory errors are cached and stop that run. A runtime error can be retried explicitly after the problem is addressed; invalid deterministic boundary proposals remain documented fallbacks.

This computer has Intel graphics and no configured CUDA inference environment. Model weight loading, GPU memory use, actual output validity and semantic improvement require a Colab run. No Qwen output has been fabricated. Dependency compatibility was checked against the published package metadata; this does not substitute for the GPU runtime test.
